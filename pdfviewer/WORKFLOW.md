# 작업 방식

사용자가 이 뷰어를 만들어 온 방식이다 (2026-11-03 ~ 11-07 세션 기록에서 정리). 규칙은 `CLAUDE.md`, 할 일은 `PLAN.md`가 기준이다.

## 한 단계를 진행하는 순서

1. **계획 먼저.** "Phase N 계획 보여줘" → 계획을 보고 고른 뒤 "구현 시작해". 단계가 크면 나눠서 진행한다 (6a/6b, 7a).
2. **직접 써 보고 확인.** 단계가 끝나면 뷰어를 띄워 실제 PDF(예: 수업 자료 `05-tools-and-function-calling.pdf`)로 써 본다.
3. **증상으로 피드백.** 고칠 점은 보이는 그대로 말한다. 예: "양 옆 폭이 일정하지 않아", "Ctrl+Tab이 안 돼", "pdf 끌어다가 안 열려". 화면 문제는 스크린샷을 잘라 붙인다.
4. **확인되면 다음으로.** "확인했어, 다음 진행해줘" 또는 "커밋해줘". 바로 확인할 수 없는 것은 미뤄 두고 넘어간다 (예: 드래그 앤 드롭은 WSLg에서 안 되므로 Phase 9의 Windows `.exe`에서 확인).

## 범위는 사용자가 정한다

- 쓰지 않을 기능은 뺀다: 인쇄, 야간 읽기(페이지 색 반전), 라이트 테마 (다크 단일).
- 쓰면서 떠오른 개선은 중간에 바로 넣는다: 검색 입력 반응 시간 단축, 썸네일 로딩 표시.
- 선택지가 있으면 추천을 듣고 고른다 ("b로 가자", "1번으로 하고 6b 진행", "추천대로 진행해줘").

## 점검

- 새 코드가 쌓이면 `/code-review`로 점검하고, 제시된 방향 중 하나를 골라 고친다.
- 화면 디자인을 손대기 전에 로직과 화면이 나뉘어 있는지 먼저 확인했다 (`tests/test_architecture.py`).

## 화면 디자인 흐름 (Phase 7)

1. 사용자가 직접 쓴 디자인 명세(스포티파이 테마)를 붙여 넣고 적용한다.
2. antislop AFTER 모드로 감사한다 → `anti-slop/audit-NNN-날짜.md`에 번호 붙은 문제 목록.
3. 고칠 번호를 고른다 ("전부 고치자"). 고친 뒤 같은 파일에 후속 보고를 붙인다.
4. 글자 크기·창 크기·높이·정렬을 명세 수치와 재서 맞춘다.
5. 실제 창을 보고 부분을 스크린샷으로 짚어 다듬는다 (예: 페이지 번호 칸 폭, 사이드바 탭 모양).

## 문서·커밋

- 문서는 요청할 때 실제 코드에 맞게 고친다 ("문서들이랑 틀린 점 있으면 수정해줘").
- PLAN 체크박스, 커밋, 푸시는 요청할 때만 한다.
