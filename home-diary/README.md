# Home Diary

아이소메트릭 방을 꾸미고, 가구를 통해 일상을 기록하고, 이웃과 집을 공유하는 소셜 웹서비스.
혼자 개발하는 포트폴리오 MVP. 이 문서가 설계안이자 진행 기록이다.

## 1. 핵심 루프

집 꾸미기 → 가구를 눌러 기록 → 포인트 획득 → 가구·집 확장 구매 → 이웃이 우편함으로 소식을 받고 집을 구경.

서비스의 차별점은 **가구 = 기록 카테고리**다. 새 가구를 사는 것은 새로운 기록 주제를 여는 것이다.

## 2. 집과 가구

### 방

- 아이소메트릭 뷰. 뒤쪽 모서리에서 두 벽이 만나고 그 앞으로 마름모꼴 바닥이 펼쳐지는 방 하나.
- Canvas 2D로 직접 그린다. 게임 엔진 없음. 구현 참고: `prototype/house-proto.html`.
- 시작 4×4. 넓히기마다 가로·세로 1칸씩 커져 최대 8×8.

| 단계 | 크기 | 가격 |
|---|---|---|
| 0 | 4×4 | 기본 |
| 1 | 5×5 | 200P |
| 2 | 6×6 | 400P |
| 3 | 7×7 | 800P |
| 4 | 8×8 | 1600P |

- 벽지와 바닥 무늬는 포인트로 사는 스킨. 종류와 가격은 M4에서 정한다.

### 가구

- 종류 8가지 × 스타일 3가지(우드·모던·빈티지) = 카탈로그 24개.
- 기록 카테고리는 **종류**에만 묶인다. 스타일은 외형 차이.
- 같은 종류는 방에 1개만 놓을 수 있다. 다른 스타일을 사면 기존 가구가 교체된다. 이전 가구는 보유 목록에 남고 환불은 없다.
- 우드를 먼저 사지 않아도 모던·빈티지를 바로 살 수 있다. 산 가구는 방에 그 종류가 없으면 자동 배치, 있으면 교체.
- 가구를 들어 올려 방에 없는 종류의 기록은 숨겨지고, 다시 놓으면 그대로 보인다. 데이터는 지우지 않는다.
- 모든 가구 1칸, 회전 없음.
- 가입 시 옷장·식탁·책상·TV의 우드 스타일을 무료 지급.

| 종류 | 기록 질문 | 기본 가격(우드) |
|---|---|---|
| 옷장 | 오늘 무엇을 입었나요? | 무료 |
| 식탁 | 오늘 무엇을 먹었나요? | 무료 |
| 책상 | 오늘 무엇을 공부·작업했나요? | 무료 |
| TV | 오늘 무엇을 봤나요? | 무료 |
| 화분 | 오늘 기분은 어땠나요? | 50P |
| 침대 | 오늘 잠은 어땠나요? | 80P |
| 책장 | 오늘 무엇을 읽었나요? | 120P |
| 피아노 | 오늘 무엇을 연주·들었나요? | 300P |

모던·빈티지 스타일은 우드 가격 + 50P(무료 종류는 100P). 숫자는 M4 밸런스 조정 대상.

- 그림은 개발 중 상자 + 아이콘. 기능 완성 후 CC0 에셋팩(Kenney 아이소메트릭 세트)으로 교체.

## 3. 기록과 포인트

- 가구를 누르면 그 종류의 질문과 과거 기록 타임라인이 열린다.
- 기록 1건 = 텍스트 + 사진 0~5장. 사진은 업로드 전 브라우저에서 긴 변 1280px로 축소해 Supabase Storage에 올린다.
- 사진 버킷은 비공개. 서버가 이웃 여부를 확인한 뒤 서명 URL을 발급한다. M2에서 처음부터 이 구조로 간다.
- 기록은 수정·삭제할 수 있다. 삭제해도 포인트는 회수하지 않고 "하루 첫 기록" 판정도 유지한다. 삭제 시 Storage의 사진도 함께 지운다.
- 포인트 규칙
  - 가구당 하루 첫 기록에만 +10P. 기록 수 자체는 무제한.
  - 하루 1건 이상 기록하면 출석. 별도 출석 버튼 없음.
  - 연속 출석은 KST 기준 전날 기록이 없으면 0으로 초기화. 7·14·21일처럼 7의 배수마다 보너스 +50P.
  - 시작 0P. 실제 결제 없음. 이웃 반응으로는 포인트를 주지 않는다(어뷰징 방지).
- "하루"는 사용자 브라우저 시간대가 아니라 서버 KST 기준으로 자른다.

## 4. 이웃과 우편함

- 이웃은 신청 → 수락인 양방향 관계.
- 이웃 찾기: 닉네임 검색(정확히 일치할 때만 결과 표시), 내 집 초대 링크 복사.
- 초대 링크 토큰은 영구이고 설정에서 재발급할 수 있다. 재발급하면 이전 링크는 즉시 무효. 비회원이 열면 가입 후 자동으로 이웃 신청되고, 그 사이 링크가 무효가 됐으면 가입은 그대로 끝내고 "링크가 만료됐어요" 한 줄만 보여준다.
- 거절하면 상대에게 알리지 않고 신청 행만 삭제한다(재신청 가능). 이웃 끊기는 양쪽 모두 가능하고, 남긴 반응·댓글은 지우지 않는다. 끊긴 동안에도 내 기록에 붙은 상대 댓글은 보이고, 다시 이웃이 되면 전부 그대로다.
- 집과 기록은 이웃에게만 공개. 비이웃은 닉네임과 집 이름만 볼 수 있다.
- 이웃이 할 수 있는 것: 집 구경, 가구별 기록 열람, 하트 반응(1인 1회), 짧은 댓글(200자).
- 우편함은 방 앞에 놓인 오브젝트. 읽지 않은 편지 수가 배지로 뜨고 누르면 목록이 열린다. 편지 종류는 네 가지뿐이다.
  1. 이웃 신청 (수락·거절 버튼 포함)
  2. 이웃이 오늘 남긴 새 기록. 이웃당 하루 1통으로 묶어 "민수가 오늘 3개 기록을 남겼어요"처럼 표시 (누르면 그 이웃 집으로 이동)
  3. 내 기록에 달린 반응·댓글
  4. 안내. 서비스가 보내는 편지(환영 편지 등)
- 피드 화면과 푸시 알림은 없다. 우편함이 유일한 알림 창구.

## 5. 계정과 첫 방문

- 닉네임 + 비밀번호(8자 이상). 닉네임은 2~12자, 한글·영문·숫자, 중복 불가, 가입 후 변경 불가. 집 이름은 언제든 바꿀 수 있다.
- Supabase Auth를 쓰되 닉네임을 내부용 이메일 `<닉네임 SHA-256 앞 32자>@home.local`로 매핑한다. 한글은 이메일 주소에 쓸 수 없어서 해시를 쓴다. 가입 트리거가 이메일과 닉네임이 맞는지 다시 검증한다. 비밀번호 찾기 없음.
- 집 이름은 1~20자. 비워 두면 "<닉네임>의 집".
- 첫 방문 흐름: 닉네임·비밀번호 입력 → 집 이름 입력 → 4×4 방에 기본 가구 4종 자동 배치 → 말풍선 한 줄 "식탁을 눌러 오늘 먹은 걸 기록해 보세요" → 첫 기록 시 +10P와 우편함에 환영 편지 1통.

## 6. 화면 구성

| 경로 | 내용 |
|---|---|
| `/login`, `/signup` | 닉네임·비밀번호 |
| `/` | 내 집. 방 캔버스 + 우편함 + 보유 가구 선반 + 기록 패널 + 상점 |
| `/h/<닉네임>` | 이웃 집(읽기 전용 + 반응·댓글). 비이웃이면 집 이름과 신청 버튼만 |
| `/invite/<토큰>` | 초대 링크. 로그인 후 자동으로 이웃 신청 |

화면 수를 늘리지 않는다. 기록·상점·우편함은 모두 내 집 화면 안의 패널이다.

## 7. 데이터 모델

Supabase Postgres. 모든 테이블에 RLS를 걸고, 이웃 여부는 `neighbors` 테이블로 판정한다.

| 테이블 | 주요 컬럼 | 비고 |
|---|---|---|
| `profiles` | id(auth.users FK), nickname(unique), house_name, points, streak, last_record_date, invite_token | 가입 시 트리거로 생성 |
| `houses` | profile_id, size(4~8), wallpaper, floor | 1인 1방 |
| `catalog` | id, kind(8종), style(3종), price, height | 정적 시드 데이터 |
| `owned_furniture` | profile_id, catalog_id | 구매·지급 내역 |
| `placements` | profile_id, kind, catalog_id, x, y | kind당 1행(unique) |
| `records` | id, profile_id, kind, text, created_at | 가구 종류 단위 |
| `record_photos` | record_id, storage_path, order | 최대 5장 |
| `neighbors` | requester_id, receiver_id, status(pending/accepted) | 양방향 1행 |
| `reactions` | record_id, profile_id | 1인 1반응 |
| `comments` | record_id, profile_id, text | 200자 |
| `mail` | receiver_id, type(request/record/reaction/notice), ref_id, day, read_at | record 타입은 (receiver, sender, day) 1행 |

포인트 지급·차감은 서버 함수(Postgres function 또는 Route Handler)에서만 하고 클라이언트는 `points`를 직접 쓰지 못한다.

## 8. 기술 스택

- Next.js (App Router), TypeScript
- Supabase: Postgres, Auth, Storage
- Vercel 배포
- 방 렌더링: Canvas 2D (라이브러리 없음)

## 9. 개발 순서

저장소는 business-agent-lab 안의 이 폴더를 그대로 쓴다. Vercel은 Root Directory를 `home-diary`로 잡는다.
각 마일스톤은 배포 가능한 상태로 끝낸다.

### 0단계. 준비 (직접 하는 일 위주)

1. business-agent-lab 저장소를 GitHub에 올려 둔다(이미 있으면 생략).
2. Supabase 프로젝트 생성, 이메일 확인 끄기, URL·anon 키·service 키 복사.
3. Vercel에 저장소 연결, Root Directory `home-diary`, 환경 변수 등록.
4. 로컬에 Node(nvm)와 Supabase CLI 설치. DB 규칙 테스트용 로컬 Supabase를 띄우려면 Docker도 필요하다.

### 1단계. M0 뼈대와 로그인

5. Next.js 프로젝트 생성, `.env.local`, Supabase 서버 클라이언트. 브라우저 클라이언트는 사진 업로드가 생기는 M2에서 만든다.
6. 첫 마이그레이션: `profiles` 테이블과 가입 트리거.
7. 가입·로그인·로그아웃 화면. 닉네임을 내부 이메일로 매핑.
8. Vercel 첫 배포. 이후 매 단계 끝에 배포가 살아 있는지 확인.

### 2단계. M1 내 집 화면

9. 프로토타입의 아이소메트릭 코드를 `lib/room/`으로 옮기고 좌표 변환·판정에 node 테스트.
10. `houses`·`catalog`·`owned_furniture`·`placements` 마이그레이션과 카탈로그 24개 시드.
11. 가입 시 4×4 방 + 기본 가구 4종 자동 배치.
12. 배치·이동을 서버 액션으로 저장. 새로고침 후 유지 확인.

### 3단계. M2 기록과 포인트

13. `records`·`record_photos` 마이그레이션, 비공개 Storage 버킷.
14. 기록 패널: 텍스트 + 사진 최대 5장(브라우저 축소 → 업로드 → 서명 URL 표시).
15. 포인트·출석 Postgres 함수. 하루 첫 기록, 연속 출석, 7일 보너스를 SQL 테스트로 검증.
16. 기록 수정·삭제와 사진 정리.

### 4단계. M3 이웃

17. `neighbors` 마이그레이션과 RLS. 비이웃이 기록을 못 읽는지 SQL로 검증.
18. 닉네임 검색, 초대 링크, 신청·수락·거절·끊기.
19. 이웃 집 화면(읽기 전용), 하트와 댓글.

### 5단계. M4 상점과 확장

20. 가구 구매·스타일 교체·들어 올리기, 집 넓히기, 벽지·바닥 스킨. 전부 서버 함수에서 포인트 검증.
21. 가격 밸런스 조정. 하루 최대 획득량 대비 가격표를 표로 계산.

### 6단계. M5 우편함과 온보딩

22. `mail` 마이그레이션, 편지 3종을 만드는 트리거(기록은 이웃당 하루 1통).
23. 우편함 오브젝트와 배지, 목록 패널.
24. 집 이름 입력 → 말풍선 → 환영 편지의 첫 방문 흐름.

### 7단계. M6 그림 교체와 마무리

25. Kenney CC0 에셋 다운로드, 24개 카탈로그에 매핑, 상자를 이미지로 교체. 우편함과 벽지·바닥 포함.
26. 폰 폭에서 캔버스 축소와 터치 확인.

### 8단계. 전체 점검

27. 신규 가입자 시나리오를 처음부터 끝까지 통과(가입 → 기록 → 이웃 → 구매 → 우편함).
28. 보안 점검: RLS 우회, 포인트 직접 수정, 서명 URL 없이 사진 접근 시도.
29. 테스트 계정 2~3개로 이웃 흐름을 실제 배포본에서 확인.

### 9단계. 포트폴리오 정리

30. README에 스크린샷, 실행 방법, 기술 선택 이유, 디벨롭 목록 정리.
31. 데모 계정 만들어 두기.

### 각 단계 공통 루틴

실패하는 테스트(아래 방침에 해당할 때만) → 마이그레이션 → 서버 → 화면 → 확인(테스트 통과 또는 배포본에서 직접 조작) → README 진행 기록 → 커밋 → 배포 확인. 막히면 멈추고 보고한다.

### 테스트 방침

기준은 하나다. "정답을 지금 문장으로 쓸 수 있고, 틀리면 아픈가?" 둘 다 예면 테스트를 먼저 쓰고(TDD), 아니면 만든 뒤 눈과 손으로 확인한다.

| 영역 | 방식 | 이유 |
|---|---|---|
| `lib/room/` 수학 (iso, tileAt, silhouette, inPoly) | TDD, Vitest | 왕복·경계 조건이 명확. 비용 거의 없음 |
| 포인트 규칙 (하루 첫 기록 +10P, 연속 출석 초기화, 7의 배수 +50P, KST 자정 경계) | TDD, 로컬 Supabase SQL 테스트 | 돈 규칙. 틀리면 데이터가 망가진 뒤 발견됨 |
| 구매·배치 규칙 (종류당 1개, 바로 구매 시 자동 배치·교체, 환불 없음, 잔액 부족) | TDD, 로컬 Supabase SQL 테스트 | 돈과 unique 제약 |
| 우편함 묶음 (이웃당 하루 1통), 초대 링크 재발급 무효 | TDD, 로컬 Supabase SQL 테스트 | 중복·경계 조건 |
| RLS (비이웃 열람 차단, points 직접 수정 차단) | 테스트 먼저, 로컬 Supabase SQL 테스트 | 보안. 8단계 28번이 이걸 돌리는 것 |
| 캔버스 그리기, 클릭 영역, 다크 모드 | 테스트 없음. 눈으로 확인 | 정답이 그림 |
| 페이지, 로그인 흐름, 사진 업로드, 서명 URL | 테스트 없음. 배포본에서 직접 조작 | 외부 서비스 접착 코드. 흉내가 코드보다 커짐 |
| `prototype/` | 테스트 없음 | 버릴 코드 |

테스트 파일 위치: `lib/room/*.test.ts`, `supabase/tests/*.sql`. 마일스톤마다 그 마일스톤 규칙만 추가한다.

### 코드 구조

- `supabase/migrations/`: 테이블·RLS·포인트 함수 SQL. 마일스톤마다 파일 하나.
- `lib/room/`: 아이소메트릭 수학과 그리기. DB를 모르는 순수 함수.
- `lib/db/`: 서버 액션이 부르는 쿼리 함수.
- `app/`: 화면 4개. 읽기는 서버 컴포넌트, 쓰기는 서버 액션. 클라이언트가 Supabase를 직접 쓰는 곳은 로그인과 사진 업로드뿐.
- 돈과 권한 규칙은 전부 DB 쪽(Postgres 함수, unique 제약, RLS)에 둔다.
- TypeScript, CSS 모듈, 상태 관리 라이브러리·게임 엔진·Tailwind 없음.
